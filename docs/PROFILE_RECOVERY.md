# 订阅切换、保存失败与节点超时

## 区分三种证据

- profiles.yaml 的 current 是 Clash Verge 选择的订阅；clash-applied.json 的 profile_uid 是稳航上次成功写入的订阅；内核 /proxies 与 /rules 才描述实际运行配置。三个状态不一致时先只读保留现场，不能据界面选中项推断当前路由。
- 原固定目标不在新订阅时，AI组 REJECT 是保护行为。除非用户明确选择新目标，否则不改变国家、解除固定或直连。
- 节点连通性须在独立内核中检查。基础服务器端口可连接不等于代理认证、TLS、传输和上游请求都成功。

## 本候选的恢复记录

活跃订阅的记录保留在顶层，其他订阅的原始内容存于 profiles，以 UID 索引。plan/apply/disable 只读取当前 UID 的原始分组、规则与撤销顺序。旧单订阅格式首次切换时归入其原有 profile_uid；关闭新订阅受管配置不会丢失其他订阅记录。

记录仍可能包含本地节点名称，不提交公共仓库。预览与写入之间若订阅身份或绑定文件发生变化，停止写入并要求重新预览；不把旧计划写到新订阅。

## 旧版本已混用的记录

升级不会凭节点名称或缺失状态猜测历史归属。管理应在停止配置写入后备份 app/config/state、clash-applied.json、profiles.yaml、runtime、相关增强文件及哈希；依据发生跨订阅切换的备份 meta.json.previous_applied 找回原订阅记录，并用新订阅首次应用前的 groups/rules/runtime 核对其独立原始内容。生成可审阅恢复记录，在副本验证两边计划与内核校验后再安装候选和原子替换记录。

如备份不足，不清空历史原始分组或自动认领另一订阅；保留当前固定边界，明确记录未解决项。用户不应被要求试错修改 YAML。

## 验证与回滚

执行 STEADYROUTE_MIHOMO 指向真实内核的 scripts/check.sh。专项 test_profile_restore.py 在独立 socket、目录和内核中重现旧版 not found，并验证新订阅保存、回到原订阅、完整撤销和持久化失败回滚。真实 TCP 端点命中边界由 test_exit_policy_core.py 验证。测试不使用真实订阅凭据。

候选后端需要独立发布验收；不直接重置旧观察期限。部署或回滚时程序、受管配置与应用记录一并处理，避免让旧程序覆盖新多订阅账本。
